# Python Stack (services, APIs, scripts)

Read together with `core.md`. These rules cover the concrete tooling for Python code and mirror the rigor of `typescript.md`. Python is a sanctioned part of the stack for backend services, APIs, data/ML work, and standalone scripts — it is not an afterthought. Every Python tool below has a direct counterpart on the TS side; the principles they implement live in `core.md`.

- **uv (environments and dependencies):** Use uv for all environment and dependency management — it is the Python counterpart to pnpm. Mixed tooling (pip here, poetry there, a hand-rolled venv somewhere else) produces "works on my machine" bugs and unreproducible installs. Manage the project with `uv` exclusively: create the environment with uv, add and remove dependencies with `uv add` / `uv remove`, run code through `uv run`, and commit the `uv.lock` lockfile so installs are deterministic. Never invoke `pip`, `poetry`, `conda`, or a raw `venv` inside a uv project.

- **Pinned, stable Python:** Pin a single, stable Python version for the project (declared in `pyproject.toml` and `.python-version`, managed by uv) and never rely on whatever interpreter happens to be on the machine. Use a stable released version, not a pre-release. A pinned interpreter is the floor every other guarantee in this file stands on.

- **pyproject.toml + PyPI packaging:** Use a single `pyproject.toml` as the one declarative source for project metadata, dependencies, and tool configuration — the counterpart to `package.json`. Resolve all third-party dependencies from PyPI through uv; never vendor packages by hand or install from ad-hoc URLs. Configure every tool (ruff, pyright, pytest) in `pyproject.toml` rather than scattering separate config files, so the whole project's setup is readable in one place.

- **Strict static typing (pyright/mypy):** Type every function signature and run a type checker in strict mode — this is the Python equivalent of TypeScript strict mode, and it is mandatory, not optional. Use pyright in strict mode (or `mypy --strict`) and treat type errors as build failures. Untyped Python silently passes the wrong shape of data deep into the system before it breaks. Annotate all parameters, return types, and attributes. Never reach for `Any`, `# type: ignore`, or `cast` to escape the checker; if you don't know the type, narrow it down. Scripts are real, type-safe programs held to the same standard — not throwaway snippets.

- **Ruff (lint + format):** Use Ruff for both linting and formatting — it replaces flake8, isort, black, and most plugins, and is the Python counterpart to ESLint plus Prettier. Enable a strict rule set in `pyproject.toml`, let `ruff format` own all formatting so the agent never formats by hand, and run `ruff check` on every save and every commit. Formatting and import ordering are decided once by the tool and never argued about again.

- **Pydantic (runtime validation):** Use Pydantic v2 for runtime validation of all external data — the Python implementation of the runtime-validation principle in `core.md`, and the counterpart to Zod. Define a Pydantic model for every external input: request bodies, API responses, message payloads, file contents, and config. Parse at the boundary, reject anything that doesn't fit, and use the model as both the validator and the static type so the shape is defined exactly once.

- **pydantic-settings (environment validation):** Use `pydantic-settings` to parse and validate all configuration and secrets at startup in a single settings module, then import that settings object everywhere. This is the Python counterpart to the Zod-based env validation on the TS side. Fail loudly at boot if any variable is missing or malformed, and never read `os.environ` directly anywhere else.

- **SQLAlchemy + Alembic (ORM and migrations):** Use SQLAlchemy 2.0 with typed, declarative models for all database access — the Python counterpart to Drizzle — and use **Alembic for all SQL schema migrations.** When a Python service owns or shares the database, its migrations must live where the Python code can run, test, and reason about them; splitting migration ownership across two tools causes the schema to drift and migrations to collide. **Whenever Python is part of the codebase, Alembic is the single source of truth for schema changes and is preferred over Drizzle's migration tooling.** Define migrations as versioned revision scripts, autogenerate them from model metadata, review every autogenerated script by hand before applying, and apply and revert them through Alembic's `upgrade` / `downgrade` so every change is ordered and reversible. Drizzle may still describe the same schema for type derivation on the TypeScript side, but it must not run migrations against an Alembic-managed database. Never let both tools write migrations to the same database.

- **FastAPI (web/API services):** Use FastAPI for HTTP services and APIs — the server-side counterpart to Next.js route handlers. Its request/response models are Pydantic, so validation, typed contracts, and the consistent API-response shape from `core.md` fall out of the framework instead of being bolted on. Keep route definitions, dependencies, and business logic in separate modules per feature. Use async handlers and async database access throughout rather than mixing sync and async I/O.

- **pytest:** Use pytest for all unit and integration testing — the Python counterpart to Vitest. Place test files alongside the code they test, use `pytest-asyncio` for async code, and prioritize pure functions and server-side logic first since they give the most value per line of test code. Run tests through `uv run pytest` so they execute against the pinned interpreter and locked dependencies.

- **pre-commit (git hooks):** Use the `pre-commit` framework to run ruff (lint + format) and the type checker on staged files before every commit — the Python counterpart to Husky plus lint-staged. Agents and developers forget to run checks manually, and bad code slips in. Keep hooks fast by scoping them to changed files so no failing code enters the repository regardless of who or what wrote it.

- **structlog (structured logging):** Use structlog to emit structured JSON logs as the concrete implementation of the structured-logging principle in `core.md`. Configure one logger in a shared module and import it everywhere. Use leveled methods with bound context fields. Never use `print()` for application logging.
