# TypeScript Stack (Next.js web apps)

Read together with `core.md`. These rules cover the concrete tooling for TypeScript/Next.js projects. When a Python service is also part of the codebase, see `python.md` — in particular, Alembic owns SQL migrations whenever Python is present, even though Drizzle still describes the schema on the TS side.

- **Next.js (App Router):** Use Next.js with the App Router for routing and server rendering. Web apps need a way to decide what shows up when someone visits a page, and Next.js turns your React components into real pages a server can send to browsers. The App Router organizes everything into folders where each folder becomes a URL path. Use it for all routing and never mix in the legacy routing system. Keep route logic, layout, and server-side operations separated into their own files within each route folder.

- **TypeScript (Strict Mode):** Use TypeScript in strict mode for type safety across the entire codebase. Code breaks when you pass the wrong type of data to a function, like handing someone a phone number when they asked for an email. TypeScript catches these mistakes before your code ever runs by making you label what type every piece of data is. Enable the strictest compiler settings available. Never opt out of type safety. If you don't know the type, figure it out and narrow it down rather than escaping the type system.

- **shadcn/ui:** Use shadcn/ui for all base UI components. Building buttons, modals, and dropdowns from scratch wastes time and creates inconsistency. shadcn/ui gives you pre-built components that live in your own codebase so you can modify them. Always install components through the CLI rather than manually copying code. Keep all UI primitives in a dedicated directory and import from there so every part of the app pulls from one source of truth.

- **Tailwind CSS:** Use Tailwind for all styling. Styling normally means jumping between markup and separate style files, which splits your attention. Tailwind puts styles directly on elements using short utility classes so you see structure and style in one place. Use utility classes exclusively. Never write custom styles unless Tailwind literally cannot express what you need. Order classes logically: layout, then spacing, then typography, then color.

- **Responsive Design:** Use a mobile-first approach for all layouts and components. Agents default to building for desktop and then awkwardly squeezing things down for smaller devices, which creates broken or unusable mobile experiences. Start with the smallest screen size and scale up using responsive utility classes and dynamic sizing. Every component should work across screen sizes without horizontal scrolling or overlapping elements. Never hardcode widths or heights when relative or fluid values would work.

- **Drizzle ORM:** Use Drizzle for all database access and schema definition. Writing raw query strings inside your code is error-prone and hard to refactor. Drizzle lets you define database tables as typed objects and query them with functions your editor can autocomplete and type-check. Organize schemas by domain with one file per table or entity group. Always derive application types from the schema so the database and app code never drift apart. Use Drizzle's migration tooling **only** when TypeScript is the sole owner of the database; if any Python service shares this database, Alembic owns migrations (see `python.md`) and Drizzle is restricted to schema definition and type derivation.

- **Zod:** Use Zod for runtime validation of all external data — this is the TypeScript implementation of the runtime-validation principle in `core.md`. Create validation schemas for every external input: forms, API responses, URL params, and config values. Place schemas next to the code that uses them. Infer TypeScript types from the schemas so you never define the same shape twice.

- **Environment Validation:** Use a Zod-based environment validation library (e.g. `@t3-oss/env-nextjs`) to parse and validate all config and secrets at build/boot time in a single dedicated file. Import config from that file everywhere and never read `process.env` directly anywhere else.

- **ESLint + TypeScript Plugin:** Use ESLint with the TypeScript plugin for static code analysis. Linting scans your code for patterns that commonly cause bugs, like unused variables, missing return types, or inconsistent imports. Use the framework-recommended config as your base, enable strict TypeScript-aware rules, and make sure formatting rules don't conflict with your formatter. Run the linter on every save and every commit.

- **Prettier:** Use Prettier for all code formatting. Teams waste time arguing about formatting opinions like tabs vs spaces, and Prettier ends the argument by reformatting all code to one consistent style automatically. Configure it once and never think about it again. The agent should never manually format code. The formatter handles it on save and on commit automatically.

- **pnpm:** Use pnpm for all dependency management. Some package managers let packages secretly use other packages they didn't declare, which causes "works on my machine" bugs. pnpm prevents this by isolating dependencies strictly so every package can only access what it explicitly lists. Use pnpm for all dependency operations. Never mix in commands from other package managers within the same project.

- **Vitest:** Use Vitest for all unit and integration testing. You need to verify your code does what you think it does without clicking through the app manually every time. Vitest runs test files that call your functions and check the outputs against expected values, and it understands your TypeScript config and path aliases out of the box. Place test files next to the code they test. Prioritize testing pure functions and server-side logic first since they give the most value per line of test code.

- **Husky + lint-staged:** Use Husky and lint-staged for automated pre-commit checks. Developers and agents forget to run the linter before committing, and bad code slips into the repository. Husky installs Git hooks that run commands automatically before every commit, and lint-staged makes those hooks fast by only checking changed files. Set up a pre-commit hook that runs formatting and linting on staged files so no failing code enters the repository regardless of who or what wrote it.

- **React Performance and Data Patterns:** Use a dedicated data fetching and caching library (e.g. TanStack Query) for all server state management. Fetching data in raw effects with manual loading and error states creates duplicated logic and poor user experience. A caching layer gives you automatic retries, deduplication, background refetching, and stale-while-revalidate behavior out of the box. Separate server state from client state. Memoize expensive computations and avoid unnecessary rerenders. Colocate state as close to where it is used as possible rather than lifting everything to the top of the component tree.

- **Structured Logger:** Use a structured JSON logger (e.g. pino) as the concrete implementation of the structured-logging principle in `core.md`. Create one logger instance in a shared utility and import it everywhere; never use `console.log` in production code.

- **Authentication:** Use a proven auth library (e.g. Auth.js / NextAuth or Better Auth) rather than building sessions, tokens, and password hashing yourself. Protect sensitive routes with Next.js middleware that runs before any route logic, per the security principle in `core.md`.
